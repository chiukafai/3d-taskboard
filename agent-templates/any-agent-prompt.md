# 把这段贴进任意 AI agent 的指令里

下面的文字不依赖任何特定产品。**WorkBuddy / Claude Code / Hermes / Cursor / 自建 agent
都能直接用**——因为它只要求 agent 会"发一个 HTTP 请求"或"往目录里写一个文件"。

把 `【】` 里的内容换成你的实际情况，然后整段加进该 agent 的系统提示 / 项目指令 / 自定义规则里。

---

## 粘贴区（从下一行开始复制）

> ### 任务上报规则
>
> 你在本次会话里**完成或推进了**任何一件事，都要把它记到 3D 看板，方便统一查看。
>
> **看板地址**：`http://【看板机器IP】:8787`
> **写令牌**：`【没有就删掉这一行】`
> **你的来源名**：`【比如 workbuddy / claude-code / hermes，必填，用于区分任务从哪来】`
>
> **怎么记**（任选一种，按你手头能力挑）：
>
> 1. 能发 HTTP 请求 → 直接 POST：
>    ```
>    POST http://【IP】:8787/api/tasks
>    Content-Type: application/json
>    Authorization: Bearer 【令牌，没有就删掉这行】
>
>    {"title":"任务标题","dept":"cfo","status":"done","priority":"high","source":"【你的来源名】","project":"【项目名】","desc":"一句话说明"}
>    ```
> 2. 能写文件 → 往 `【看板目录】/data/inbox/` 里写一个 `.jsonl` 文件，一行一个任务对象（字段同上）。
> 3. 会跑命令 → 执行 `【看板目录】/agent-templates/curl.sh "任务标题" cfo done high`。
>
> **写之前先判一下这条归谁（这一步别省）**
>
> `dept` 不要随手猜着写，按这个顺序判：
> 1. **谁验收 → 就是 `dept`。** 做完这件事，是谁拍板说"行"？
>    财务报表→`cfo`；接口部署→`cto`；投放文案→`cmo`；发货库存→`coo`；
>    需求原型→`cpo`；合规合同→`cro`；年度规划→`ceo`；跨部门评审会→`meeting`
> 2. **谁给料 → 写 `collaborators`。** 需要别的部门提供数据/审批/接口时填数组，如 `"collaborators":["cfo","cto"]`。
> 3. **判不出来就别硬编。** 要么**不写 `dept`**（让系统按关键词猜，看板会打「部门待核」灰标提醒人复核），
>    要么写最近的那个部门并用 `dept_reason` 说明理由（≤80 字）。
>
> 口诀：**`dept` = 谁验收；`collaborators` = 谁给料。**
> 拿不准时宁可写 `collaborators` —— 协作错了只是少条线，归属错了是整条任务进错房间。
>
> **字段速查**
> - `title` 必填
> - `dept`：`ceo` `cfo` `cto` `cpo` `cmo` `coo` `cro` `meeting`；写中文（`财务`/`技术`/`营销`）也认
> - `status`：`todo` / `in_progress` / `done` / `blocked`，写中文（`待办`/`进行中`/`已完成`/`阻塞`）也认
> - `priority`：`high` / `medium` / `low`，写 `高`/`中`/`低` 也认
> - `dept_reason`：可选，一句话说明你判部门的依据（人会在看板上看到）
> - 其余可选：`desc` `project` `due` `tags` `collaborators` `external_id`
>
> **三条纪律**
> 1. **未完成的也要记**——不要只记成功的事。没做完的用 `status: in_progress`，卡住的用 `blocked`。
> 2. 同一件事**再记一次不会变两条**——系统按「部门 + 标题（或 external_id）」去重，重复上报等于更新。
>    所以状态变了就直接再报一次。
> 3. 一次会话**尽量 3 条以内**（合并同类项）；只有标题没把握时才补充 `desc`。不要为了凑数硬造任务。
>
> ### 如果你还想主动接活（可选，不用就删掉这节）
>
> 看到看板上属于你部门的待办任务，你可以**申请接手**，但**不能自己开工**——
> 是否放行由人决定，这是刻意的（防止任务被悄悄领走）。
>
> 1. 找活：`GET http://【IP】:8787/api/tasks?status=todo&dept=你的部门&claim=none`
> 2. 提申请：`POST http://【IP】:8787/api/tasks/<任务id>/claim`
>    body：`{"agent":"【你的来源名】","note":"为什么你能接 / 打算怎么做"}`
>    → 返回 `result: "proposed"`。**此时任务仍是待办，不要开始干活。**
> 3. 等批准后取活：`GET http://【IP】:8787/api/queue?agent=【你的来源名】`
>    **只有出现在这里的才是已批准、可以开工的。** 干完照常用上面第 1 步上报 `status:done`。
>
> 申请被驳回（`rejected`）就停手，别重试——`reason` 里有原因。
> 详细规则见 `【看板目录】/agent-templates/SPEC.md` §5。
>
> 会话收尾时，用一句话汇报你上报了几条、有没有失败。

## 为什么这样设计成"不绑定"

| 常见做法 | 问题 | 本方案 |
|---|---|---|
| 写死在 `~/.某agent/` 目录 | 换个 agent 就失效 | 地址、令牌、来源名都是**参数**，不是路径 |
| 只认一种工具调用 | 别的 agent 没这个工具 | 只依赖 **HTTP** 和 **写文件** 两种最底层能力 |
| 要求固定 JSON Schema | agent 记不住就放弃上报 | 只强制 `title`，其余全可省，且认中英文别名 |
| 每次上报都新增 | 看板很快被重复项淹没 | 唯一键去重，重复上报 = 更新 |
| 让 agent 自己判断该谁做 | 判错了也没人知道 | **判 + 标**：显式写的信任，猜的打「部门待核」标给人复核 |
| agent 自己"接活"就开工 | 任务被悄悄领走，人失去审核机会 | **认领协议**：agent 只提申请，人批准才开工（§5） |
